# Huston Logic website: permanent rules

Marketing site for Huston Logic (one-person consultancy for custom websites and workflows, Grant Huston). Next.js App Router, strict TypeScript, Tailwind CSS v4, **static export** deployed on **Cloudflare Workers**. Merging a pull request into `main` deploys automatically through Cloudflare Workers Builds; other branches get preview URLs. Never run `wrangler deploy` by hand. Read this file before changing the repo, and update it when a rule changes.

## Sources of truth

It is a set of changes on top of the copy already in `src/content/`; anything it doesn't mention stays as it is. `docs/website-plan.md` (Revision 7.1) is history: it explains the base copy but no longer overrides it. Preserve copy verbatim.
- **Design:** `docs/STYLE-GUIDE.md` (style guide v3, with the Revision 8 motion amendment in §9), then the Revision 8 Home mockups in `design-v3/reference/rev8/` (layout, order and spacing at 390 and 1440 wide; build with this repo's components and tokens, never their inline styles) and the v3 first screen in `design-v3/reference/home-top.html`. The logo files are in `public/brand/`; never redraw the mark. Where this file and those two disagree on copy or design, they win.
- **Pricing:** no price anywhere on the site (Revision 8). Prices are discussed in person.
- **Contact form:** `src/components/hl/ContactForm.tsx` posts JSON to the contact Worker (`POST /api/contact`, `worker/contact.ts`, website-plan E6), which verifies Turnstile, sends the lead to Grant's Pipeline app (`worker/intake.ts`; the Google Sheet is the fallback while `INTAKE_SECRET` is unset or the app fails), emails Grant and sends the B7b automatic reply. The other forms an owner adds (none yet) use a different route and are described under Architecture ("Forms"); they never change what this form does.

## Architecture

- `output: "export"` in `next.config.ts`. The Next.js site is 100% static: no API routes, no server actions, no runtime server code, no `next/image` optimization (images are `unoptimized`; ship pre-sized files). Server-side needs go to an external provider (scheduler, analytics) or, for the contact form, the Worker.
- `worker/` is the only server code. Its entry is `worker/index.ts`, which sends `/api/*` through `worker/api.ts`: `/api/forms/<id>` goes to the forms route (`worker/forms.ts`), and every other `/api` path, `/api/contact` included, goes straight to the contact Worker (`worker/contact.ts`, unchanged by the editor and by the forms route), and, only in production on the site's own domain with `editor.enabled` true, runs the site editor (`worker/editor/`: the MCP endpoint `/mcp`, the owner page `/owner`, OAuth under `/oauth/*` and `/.well-known/oauth-*`; docs/EDITING.md). `worker/index.ts` is the one file that imports the OAuth library. `wrangler.jsonc` runs the Worker for `/api/*` only (`run_worker_first`) until the editor is turned on; `npm run sync:config` then adds the editor's paths and bindings, and while `editor.enabled` is false it adds none. The editor's settings are read through `worker/config.ts` from `site.config.ts` (the `editor` block, `domain` and `business`); the contact Worker keeps reading its own settings and is not affected; the forms route reads the `forms` caps and the `contact` names it needs (`siteEmail`, `fromName`, `replyFromName`, `pipelineUrl`, `sheetTabs`) through the same file. `worker/` has its own `tsconfig.json`, generated runtime types (`npx wrangler types worker/worker-configuration.d.ts`; regenerate after changing `wrangler.jsonc`) and tests on Node's built-in runner (`worker/*.test.ts` (including `worker/forms.test.ts` for the forms route), `worker/editor/*.test.ts`, `worker/uploads/*.test.ts`; mocked `fetch`, a fake GitHub and fake storage, never real mail, data or accounts; the editor tests seed settings and example items from `worker/editor/fixtures/`, not from `src/content`). It uses no libraries except `@cloudflare/workers-oauth-provider` (the editor's OAuth server, imported only by `worker/index.ts`): Web Crypto for the Google JWT and the GitHub App token, `fetch` for Turnstile, Resend, Sheets, the Pipeline app and GitHub. It may import only modules from `src/` that import only each other (no Node, Next or library imports) and the import-free `site.config.ts`: the contact Worker's `content/contact-fields.ts`, `content/auto-reply.ts`, `content/providers.ts`, `lib/contact-validation.ts` and `lib/first-name.ts`, and, for the editor, `lib/thanks-links.ts`, `lib/pdf-scan.ts`, `blocks/*.ts` (schema, validate, definitions, embeds), the `blocks/library/<type>/definition.ts` files and `site-blocks/*.ts`, `collections/*.ts`, `brand/*.ts`, `settings/*.ts`, `forms/*.ts` and `content/forms.ts` (never their tests), with explicit `.ts` extensions, so the site and the Worker share one set of rules. Never import `site.ts` there (it reads `process.env`). The notification email is plain text only; the automatic reply is the one HTML email, a fixed template in which the only visitor input is the escaped first name, and its logs hold fixed event names and status codes, never personal data or secrets. The editor's upload inbox lives in `worker/uploads/` (an R2 bucket `UPLOADS` and the Images binding `IMAGES`, only with `editor.uploads.enabled`), and files reach the repo only through a proposal, as `public/images/uploads/<id>.webp` or `public/files/<slug>-<id>.pdf`. The editor and uploads are off: no account value, bucket, KV namespace, GitHub App, Access application or secret exists for them yet.
- `src/app/` routes only: pages, `layout.tsx`, `sitemap.ts`, `robots.ts`, `not-found.tsx`, `og.png/route.tsx`, `grant.vcf/route.ts`, `icon.svg`. Route files compose components and content; they hold no copy. Every site page lives in the `(site)` route group, whose layout adds the header, `main#main` and footer (`SiteChrome`; the 404 wraps itself in it too). `/card` (the NFC business card, copy in `card.ts`) sits outside the group: no site nav, noindex, not in the sitemap, and it links to the build-time contact file `/grant.vcf` (headers in `public/_headers`).
- `src/content/` holds **all copy and site settings** as typed TypeScript modules (`home.ts`, `systems.ts`, `services.ts`, `past-work.ts`, `about.ts`, `contact.ts`, `contact-fields.ts`, `auto-reply.ts`, `insights.ts`, `privacy.ts`, `site.ts`, `providers.ts`, `nav.ts`, `card.ts`). Edit copy here, never inline in JSX. Provider settings (`email` (the notification address), `schedulerUrl`, `turnstileSiteKey`) live in `providers.ts`; `site.ts` re-exports them. The public email and the LinkedIn link live in `src/content/business.json` (read through `getBusiness()`); the colors and fonts in `src/content/brand.json`, which `npm run sync:config` turns into `src/app/palette.css` (the only place the `:root` palette is set); the site notice in `src/content/notice.json`. Collection items are one JSON file each under `src/content/collections/<kind>/` (testimonials today; the template's posts, videos, episodes and team kinds are defined in `src/collections/` and have no items here yet); the list blocks read them at build time (`src/lib/site-content.ts`, `src/lib/collections.ts`). Business details, brand and the notice are read through `src/lib/settings.ts` (`getBusiness()` and friends). An item or page with `status` `archived` is not built and leaves lists, menus and the sitemap, and its file stays so it can be restored: never delete an item or page file to remove it. The site's own item fields are declared in `src/site-blocks/collection-fields.ts`.
- **Forms** are data too. Each form is one JSON file in `src/content/forms/<id>.json` (the contact form is `contact.json`, form id `contact`; it is the only one today). Its rules are in `src/forms/` (import-free, so the content check, the editor and the Worker share them). `src/forms/registry.generated.ts` lists the forms for the Worker; it is generated by `npm run sync:config`, written by the editor when a form is added, and committed. The `form` block (`src/blocks/library/form/`) shows a form on a page. **Two routes, one set of rules:** `POST /api/contact` stays the contact form's own handler (`worker/contact.ts`: its 16 KB limit, the Pipeline app first with the Sheet as fallback, the B7b automatic reply). `POST /api/forms/<id>` (`worker/forms.ts`) serves every other form, with the same layers (same-origin, body limit `forms.maxBodyBytes`, the contact rate limiter pair with a key per form, honeypot, the shared validator `src/forms/validate.ts`, server-side Turnstile with action `form`, formula guard on Sheet cells, a plain-text notification) and the same save chain: the Pipeline app first (production only, while `INTAKE_SECRET` is set), then the Sheet as the fallback (tabs `Forms` and `Forms preview`, `contact.sheetTabs`), the notification email always, and, for a download form, one plain-text download email whose link is built from `domain.url`, never the request. With no form file besides `contact.json`, every `/api/forms/<id>` answers 404 (an unknown form is refused before anything is read). The contact form's special behaviour is code, bound to the id `contact`. Personal-data rules are in `src/forms/sensitive.ts`. See docs/EDITING.md, "Forms".
- **The blog is off.** The template's blog (`/blog`, `/blog/feed.xml`, `src/content/pages/blog.json`, example posts) is not on this site: a Next.js static export needs at least one generated address for a dynamic route, so the `/blog` route cannot sit in the build silently, and a live page would show placeholders. The blog's code in `src/lib/blog.ts`, `src/lib/feed.ts`, `src/components/hl/Post*.tsx` and the `post-index` and `latest-posts` blocks is in place. To turn it on, add real words in `blog.json`, then posts, then bring in `src/app/(site)/blog/` from the template (a separate, reviewed change).
- `src/components/hl/` the v3 design primitives and page sections; `src/components/layout/` header, footer, nav and the badge turn; `src/components/ui/` copy helpers (`Text`, `Placeholder`, `JsonLd`, `InViewOnce`, `BookCallButton`); `src/components/illustrations/` decorative SVG. Prefer a new small reusable component over repeating markup. Server Components by default; add `"use client"` only for real interactivity (currently: `HeaderNav`, `BadgeTurn`, `InViewOnce`, `PointerTilt`, `SectionNav`, `ContactForm`, `ThanksText`). Keep client JS minimal.
- `src/lib/` pure helpers (`metadata.ts`, `collections.ts`, `settings.ts`, `site-content.ts`, `jsonld.ts`, `placeholders.ts`, `fonts.ts`, `framework.ts`, `routes.ts`, `vcard.ts`, `contact-validation.ts`, `first-name.ts`, `contact-handoff.ts`).
- `scripts/` Node scripts: `check-placeholders.mjs` (launch gate), `preview.mjs` (static preview server that also applies the `/*` block of `public/_headers`).
- `tests/a11y/` Playwright + axe accessibility check (CI job `a11y`, run against the built site via `scripts/preview.mjs`); `playwright.config.ts`. `src/lib/routes.ts` is the single route list used by `sitemap.ts`, the accessibility test (`auditRoutes` plus the noindex routes, which include the `/blocks` showcase) and Lighthouse; it reads the page files.
- `lighthouserc.cjs` Lighthouse CI config (CI job `lighthouse`; pages come from `src/lib/routes.ts`: `auditRoutes`; the noindex `/blocks` showcase is not audited, it scores below the performance threshold); `scripts/lighthouse-summary.mjs` writes the score table to the job summary.
- `public/_headers` is the Cloudflare Workers header config. `.github/workflows/ci.yml` runs the checks.
- Design tokens (colors, type scale, radii, shadows) are defined once: the palette and Tailwind theme in `src/app/hl.css`, the base layer (body, headings, focus ring) in `src/app/globals.css`. Use the tokens (`ink`, `silver`, `green`, `rust`, `tint`, `hairline`, ...); never hard-code hex values in components (the OG image route is the one exception because it cannot use CSS). Fonts (Outfit for headings and UI, Inter for body, Newsreader italic for the second voice; no others) are declared only in `src/lib/fonts.ts` through `next/font/google`, which self-hosts them at build time. No third-party font or script tags, with one exception: Cloudflare Turnstile (`https://challenges.cloudflare.com`), which `src/components/hl/useTurnstile.ts` loads only after the visitor focuses the contact form.

## Security rules

- No secrets in the repo, in `NEXT_PUBLIC_*` variables, or in client code. The only env var is `NEXT_PUBLIC_SITE_URL` (public). `.env*` files are git-ignored except `.env.example`.
- `public/_headers` must keep: CSP, `X-Content-Type-Options`, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy`, `Permissions-Policy`, HSTS, COOP/CORP. The CSP needs `'unsafe-inline'` for scripts/styles only because the Next.js static export inlines its bootstrap scripts. Do not loosen it further. When adding a provider (scheduler iframe, form endpoint, analytics script) add only the exact origin it needs (`frame-src`, `connect-src`, `script-src`) in the same change and document it in the README.
- External links (`http(s)://`) must use `target="_blank" rel="noopener noreferrer"`. `Button` does this automatically; hand-written anchors must too.
- **Contact form Worker.** Secrets (`RESEND_API_KEY`, `TURNSTILE_SECRET_KEY`, `GOOGLE_SERVICE_ACCOUNT_KEY`, `GOOGLE_SHEET_ID`, and `INTAKE_SECRET` for the Pipeline app) exist only as Worker secrets that Grant sets himself (`wrangler secret put`, and `wrangler preview base-config secret put` for previews; previews never call the app); `wrangler.jsonc` lists names only, and `INTAKE_SECRET` is not in `secrets.required` until Grant says so. The rate limiter namespace ids (2101, 2102) are unique in Grant's account because the same id shares counters across Workers; never reuse another Worker's id. Keep every layer: same-origin check, size limit, rate limit, honeypot (an honest error, never a pretend success), the shared validation, server-side Turnstile with hostname and action checks, RAW Sheet input with the formula guard, a plain-text notification, and an automatic reply whose HTML is a fixed template (the escaped first name is the only visitor input; the booking link comes from `providers.schedulerUrl`, never the request origin). Preview mode must never email anyone but the site's own address or write to the `Submissions` or `Forms` tab (previews use `Preview` and `Forms preview`). The forms route (`POST /api/forms/<id>`, `worker/forms.ts`) keeps every one of these layers, with Turnstile action `form`, and its download email is plain text with no visitor input (the link comes from `domain.url`, never the request); `worker/contact.ts` and its senders are not changed by it. Never ask visitors to submit sensitive data (client or health records) through the form.
- **Site editor** (docs/EDITING.md; off until `editor.enabled`, and it does not touch the contact form). One GitHub App per site, installed on that site's repo only, with five permissions: Contents, Pull requests and Issues read and write; Checks and Metadata read only. ## Motion rules

The motion design is `docs/STYLE-GUIDE.md` §9. The rules below are the guardrails. The static design is always the resting state: every animation must end exactly in it, and removing a rule must never change how a page looks.

- **Where it lives.** Keyframes, the door, tilt and menu-panel (`.panel`) rules and the "Revision 8 section motion (§9.4)" block are in `src/app/hl.css`; the shared timing tokens (`--ease-site`, `--duration-feedback`, `--duration-panel`) are in `src/app/globals.css`, and Tailwind's default transition uses them, so a plain `transition-colors` is already compliant. Add new motion by extending these, not per page.
- **One moment per section, played once (Revision 8, STYLE-GUIDE §9.4).** Each section may have one orchestrated moment, released once by `InViewOnce` (or page load for the hero), and it must show something happening in the product or the process, never decoration. No loops. The framework icons are static.
- **Never hide content behind motion.** Body copy, actions and links are in the initial HTML. Headline and hero intros are CSS keyframes with `both`/`backwards` fill, so they need no JS. A section moment may hold its elements at a start frame (bubbles or chips at opacity 0, say) only behind both the `html.js` class (set by an inline script in `<head>` before first paint) and `prefers-reduced-motion: no-preference`, released by `InViewOnce`; without JS, or with reduced motion, everything shows.
- **Reduced motion.** `prefers-reduced-motion: reduce` sets `animation: none` and `transition: none` globally (end of `hl.css`), so the end state shows immediately, and the badge turn and door swing are switched off. Any new animation must be safe under that rule (no state that only a running animation reveals).
- **Scrolling stays native.** The only scroll listener is the passive one in `BadgeTurn` (STYLE-GUIDE §9.3, off under reduced motion). No scroll hijacking, scroll-linked effects or wheel/touch listeners; use `IntersectionObserver` (via `InViewOnce`) for reveal-on-view.
- **No motion libraries.** CSS transitions and keyframes only.

- Fix a failing `a11y` or `lighthouse` job at its cause. Do not loosen a threshold or add a `known-issues.ts` entry just to get green.
- `.github/workflows/**`, `.claude/hooks/**`, `.claude/agents/**`, `.claude/skills/**` and `.claude/settings*.json` are owner-edited: Claude's hooks block changes to them, so a workflow or hook change is written to the scratchpad and copied into place by the owner (see CLAUDE.md and `.claude/hooks/README.md`).

CI (`.github/workflows/ci.yml`) runs `check` (lint, typecheck, build, a check that the deploy artifacts exist: `out/index.html`, `404.html`, `sitemap.xml`, `robots.txt`, `_headers`, and an informational placeholder report), plus `a11y` and `lighthouse`, on every PR.

## Maintenance

- Upgrading Next.js: read the bundled docs in `node_modules/next/dist/docs/` first, then re-run `npm run check`, re-test the static export (`npm run preview`) on every route, and re-verify the CSP in the browser console.
- Adding a page: content module in `src/content/`, route in `src/app/<route>/page.tsx` using `pageMetadata`, nav/footer entry if needed, add the route to `src/lib/routes.ts` (feeds the sitemap and the accessibility check), and a check that it renders with no console errors at mobile and desktop widths.
- Adding an Insights article: Insights is currently a "coming soon" page. The planned article format (short-version box, "Try this this week" callout, author box, CTA, related articles, `BlogPosting` JSON-LD with real published/reviewed dates) is described in the V1 copy doc; add routes, sitemap entries and a content type then. Never invent statistics; label hypothetical examples; anonymize client details.
- Launch checklist lives in the README. Every merge into `main` is a production deploy through Cloudflare Workers Builds (settings in the README's "Deploy to Cloudflare Workers" section); never run `wrangler deploy` by hand, and the owner merges.
